# P6.2 — macOS Multi-VM: Process-Per-VM with Shared Memory

> **Status**: Complete (Phase A ✅, Phase B ✅, Phase C ✅, Phase D ✅)
> **Phase**: P6.2 (follows P5 cross-platform VMM refactor, P6 shell/attach wiring)
> **Goal**: Run multiple VMs simultaneously on macOS, enabling docker compose and multi-container workloads

## Problem Statement

Apple's Hypervisor.framework (HVF) enforces a **one-VM-per-process kernel constraint**. `hv_vm_create()`
is process-global — calling it twice returns `HV_BUSY` (0xfae94002). This is a hard kernel limitation,
not a software bug.

On Linux, KVM has no such constraint — `KVM_CREATE_VM` returns a new fd each call, unlimited VMs per
process. Visor's entire architecture (VMs-as-threads, CoW memory, shared virtqueues) depends on
multi-VM-in-one-process.

**Without this plan, visor on macOS is limited to one VM at a time.** Docker compose, multi-container
apps, and any real development workflow are impossible.

### What Every macOS VMM Does

| Tool        | Architecture                                          | VM Isolation           |
| ----------- | ----------------------------------------------------- | ---------------------- |
| Lima (QEMU) | 1 `limactl hostagent` per VM → spawns `qemu-system-*` | Process boundary       |
| Lima (VZ)   | 1 `limactl hostagent` per VM → VZVirtualMachine       | Hostagent process      |
| Colima      | Thin wrapper → delegates to Lima                      | Same as Lima           |
| Tart        | 1 `tart run` per VM → VZVirtualMachine                | Process boundary       |
| Apple CLI   | 1 launchd XPC service per container                   | launchd supervision    |
| Firecracker | 1 process per VM (jailer)                             | Process boundary       |
| CrosVM      | 1 process per VM + forked device processes            | Process + device       |
| OpenVMM     | Multi-process mesh (control + per-VM workers)         | Mesh channels over UDS |

**Every macOS VMM uses separate processes.** The question is how to do it while preserving visor's
advantages.

### Options Evaluated

| Option                               | Verdict      | Reason                                                            |
| ------------------------------------ | ------------ | ----------------------------------------------------------------- |
| A. Use Virtualization.framework (VZ) | Rejected     | Zero vCPU register access, no VM exits, no custom devices         |
| B. Naive fork-per-VM                 | Loses value  | No shared memory, loses CoW/pool/inter-VM advantages              |
| C. VM multiplexing in one HVF VM     | Infeasible   | Stage-2 page tables global, TLB flush, 6-12 months, security risk |
| D. Nested virtualization in guest    | Too indirect | Loses direct HVF control                                          |
| **E. Fork-per-VM + shared memory**   | **Agreed**   | **Preserves nearly all visor advantages**                         |

## Architecture

### Dual-Mode Design

```text
LINUX (unchanged — single-process, multi-VM):

  visor daemon (PID 100)
  ├── API server, OCI, pool, networking
  ├── vm-1-vcpu-0 thread    ← KVM_CREATE_VM fd=3
  ├── vm-1-vcpu-1 thread
  ├── vm-2-vcpu-0 thread    ← KVM_CREATE_VM fd=4
  └── vm-2-vcpu-1 thread


macOS (NEW — process-per-VM with shared memory):

  visor daemon (parent process)
  ├── API server, OCI, pool, networking
  ├── shm_open("visor-mem-{vm-id}") → shared memory backing
  │
  ├── VM worker 0 (child process: visor --vm-worker)
  │   ├── hv_vm_create()           ← its OWN HVF VM
  │   ├── mmap(shm_fd, MAP_SHARED) ← shared with parent
  │   ├── hv_vm_map(region)         ← maps shared mem as guest RAM
  │   └── vCPU threads
  │
  ├── VM worker 1 (child process: visor --vm-worker)
  │   ├── hv_vm_create()           ← independent HVF VM
  │   ├── mmap(shm_fd, MAP_SHARED)
  │   └── vCPU threads
  │
  └── ...N workers
```

### What's Preserved vs Lost

| Benefit          | In-Process (Linux)  | Shared-Mem Workers (macOS)       | Delta      |
| ---------------- | ------------------- | -------------------------------- | ---------- |
| CoW snapshots    | `mmap(MAP_PRIVATE)` | Identical (mmap snapshot file)   | None       |
| Inter-VM memcpy  | Direct, ~10μs       | Shared ring buffer, ~11μs        | ~1μs       |
| Pool grab        | Assign thread, <1ms | IPC to pre-forked worker, <1ms   | ~100μs     |
| Snapshot restore | <5ms                | Identical                        | None       |
| Crash isolation  | One crash risks all | One crash kills one VM           | **Better** |
| Memory overhead  | Zero per-VM         | ~2MB per worker process          | Small      |
| File descriptors | Shared process      | Inherited via fork or SCM_RIGHTS | None       |

**Key insight**: Shared memory (`shm_open` + `mmap(MAP_SHARED)`) preserves nearly all the
single-process advantages. The parent and all workers see the same physical pages. CoW snapshots
still work — `mmap(MAP_PRIVATE, snapshot_fd)` is per-process but the snapshot file backing is
shared via page cache.

### Crash Isolation (Hard Requirement)

The user declared crash isolation a hard requirement: "if all VMs crash because one crashed thats
a no go!"

**Current state (single-process)**:

- Rust thread panics are isolated (thread dies, others continue)
- `unsafe` code bugs (mmap, KVM ioctls) can corrupt shared process state
- No `catch_unwind()` on vCPU run loop
- One bad `unsafe` block kills ALL VMs

**With process-per-VM**:

- Worker process crash kills only that one VM
- Parent daemon stays alive, manages remaining VMs
- OS enforces isolation — no shared mutable state between workers
- `waitpid()` in parent detects worker death, cleans up resources

## VmLifecycle Trait Abstraction

Inspired by OpenVMM's `VmmMesh` pattern with `--single-process` flag.

```rust
/// Platform-specific VM lifecycle management.
///
/// On Linux, VMs run as threads in the daemon process (in-process model).
/// On macOS, each VM runs in a separate worker process due to HVF's
/// one-VM-per-process kernel constraint.
#[async_trait]
pub trait VmLifecycle: Send + Sync {
    /// Boot a new VM with the given configuration.
    ///
    /// Returns a handle for managing the VM's lifecycle.
    ///
    /// # Errors
    ///
    /// Returns error if VM creation fails (resource exhaustion,
    /// invalid config, hypervisor error).
    async fn boot(&self, config: VmConfig, resources: VmResources) -> Result<VmHandle>;

    /// Stop a running VM gracefully.
    ///
    /// # Errors
    ///
    /// Returns error if the VM is not running or stop signal fails.
    async fn stop(&self, id: &VmId) -> Result<()>;

    /// Kill a VM immediately.
    ///
    /// # Errors
    ///
    /// Returns error if the VM is not running.
    async fn kill(&self, id: &VmId) -> Result<()>;

    /// Get the communication channel to a VM (vsock).
    ///
    /// # Errors
    ///
    /// Returns error if the VM is not running or channel unavailable.
    async fn comms(&self, id: &VmId) -> Result<Box<dyn CommsChannel>>;
}
```

**Implementations:**

- `InProcessLifecycle` (Linux) — current code, VMs are threads, direct function calls
- `WorkerProcessLifecycle` (macOS) — fork/exec `visor --vm-worker`, communicate via Unix socket

The rest of visor-runtime (`backend.rs`, `api/`, `cli/`, `pool/`, `compose/`) calls only `VmLifecycle`
methods. They are completely unaware of the process model.

## Workstreams

### WS1 — VM Worker Binary Mode ✅

**Priority**: P1 | **Effort**: 2-3 hours (AI agent)

Add `--vm-worker` hidden subcommand to visor binary. When invoked, the process:

1. Reads `VmWorkerConfig` from stdin (JSON)
2. Opens inherited shared memory fd
3. Calls `hv_vm_create()` — owns the HVF singleton for this process
4. Maps shared memory into HVF guest address space
5. Boots the VM (kernel, devices, vCPU run loop)
6. Communicates with parent via Unix socket (control channel)
7. Exits when VM terminates or parent sends shutdown

**Files:**

- `crates/visor-runtime/src/cli/vm_worker.rs` (new) — worker entry point
- `crates/visor-runtime/src/main.rs` — add `--vm-worker` dispatch

**Control protocol** (parent ↔ worker, over Unix socketpair):

```text
Parent → Worker:
  { "type": "boot", "config": VmWorkerConfig }
  { "type": "stop" }
  { "type": "kill" }
  { "type": "exec", "request": ExecRequest }

Worker → Parent:
  { "type": "ready", "pid": 1234 }
  { "type": "vm_exit", "code": 0 }
  { "type": "exec_result", "result": ExecResult }
  { "type": "error", "message": "..." }
```

**Acceptance**: `visor --vm-worker` boots a VM from config on stdin, responds with "ready" on control
socket.

### WS3 — WorkerProcessLifecycle (macOS)

**Priority**: P1 | **Effort**: 4-6 hours (AI agent)

Implement `WorkerProcessLifecycle` that:

1. `boot()` → fork/exec `visor --vm-worker`, passing config + shared memory fd
2. Monitors worker via `waitpid()` (non-blocking, tokio task)
3. `stop()` → sends `{ "type": "stop" }` over control socket
4. `kill()` → sends `SIGKILL` to worker PID
5. `comms()` → proxies vsock over control socket (or direct UDS passthrough)

**Files:**

- `crates/visor-runtime/src/lifecycle/worker_process.rs` (new) — macOS impl
- `crates/visor-runtime/src/lifecycle/mod.rs` — factory selects impl based on `#[cfg(target_os)]`

**Acceptance**: On macOS, `visor run alpine echo hello` works. `visor run -d` + second `visor run -d`
both stay running simultaneously.

### WS4 — Shared Memory for Guest RAM

**Priority**: P1 | **Effort**: 3-4 hours (AI agent)

Replace anonymous mmap with named shared memory for guest RAM on macOS:

1. Parent creates `shm_open("/visor-vm-{id}", O_CREAT | O_RDWR)`
2. `ftruncate(shm_fd, memory_size)`
3. Pass `shm_fd` to worker via `Command::pre_exec()` fd inheritance
4. Worker mmaps the shared fd and maps it into HVF guest address space
5. Parent can read/write guest memory directly (for snapshot save, dirty tracking)

**Files:**

- `crates/visor-vmm/src/memory.rs` — add `SharedMemoryRegion` variant
- `crates/visor-runtime/src/lifecycle/worker_process.rs` — shm creation + fd passing

**Acceptance**: Parent process can read guest memory written by worker's VM. `hexdump` of
`/dev/shm/visor-vm-*` shows guest memory contents.

### WS5 — Inter-VM Shared Ring Buffers

**Priority**: P2 | **Effort**: 4-6 hours (AI agent)

For inter-VM networking on macOS, use shared ring buffers in named shared memory:

1. Create `/visor-net-{network-id}` shared memory region
2. Ring buffer per VM pair (producer/consumer with atomic indices)
3. Each worker mmaps the network shared region
4. virtio-net device reads/writes from ring buffer instead of TAP
5. `eventfd` (Linux) or `kqueue` (macOS) for wakeup notification

**Files:**

- `crates/visor-vmm/src/net/shared_ring.rs` (new) — lock-free ring buffer
- `crates/visor-vmm/src/net/macos.rs` — wire ring buffer to virtio-net

**Acceptance**: Two VMs on same network can `ping` each other. Latency <15μs.

### WS6 — Pre-Fork Pool for Sub-ms Warm Grab

**Priority**: P2 | **Effort**: 3-4 hours (AI agent)

Pre-fork worker processes that sit idle until assigned a VM:

1. Daemon forks N worker processes at startup (configurable, default 3)
2. Workers call `hv_vm_create()` but don't boot — wait on control socket
3. Pool grab → send boot config to idle worker → VM starts immediately
4. Background task maintains target pool size (refills as workers are consumed)

**Files:**

- `crates/visor-runtime/src/lifecycle/worker_pool.rs` (new) — pre-fork pool
- `crates/visor-runtime/src/lifecycle/worker_process.rs` — deferred boot support

**Acceptance**: Second `visor run` (pool hit) completes in <5ms on macOS.

### WS7 — Catch-Unwind for vCPU Run Loop

**Priority**: P2 | **Effort**: 1-2 hours (AI agent)

Add `catch_unwind()` around the vCPU run loop on both platforms:

1. Wrap `run_vcpu()` in `std::panic::catch_unwind(AssertUnwindSafe(|| ...))`
2. On panic: log error, set VM state to `Failed`, clean up resources
3. On Linux: prevents one VM's panic from taking down the daemon
4. On macOS: additional safety layer (process boundary already isolates)

**Files:**

- `crates/visor-vmm/src/vm/mod.rs` — wrap `run_vcpu()` call
- `crates/visor-vmm/src/vm/macos.rs` — wrap vCPU loop

**Acceptance**: Test that intentionally panics in vCPU handler doesn't crash daemon.

## Implementation Order

```text
Phase A (Foundation):     WS2 ✅ → WS1 ✅ → WS8 ✅
Phase B (Multi-VM):       WS3 ✅ → WS4 ✅ → WS9 ✅
Phase C (Performance):    WS6 ✅ → WS5 ✅
```

**Rationale**: Extract the trait first (WS2) since it's a pure refactor with no behavior change. Then
build the worker mode (WS1) and codesign (WS8). Then wire them together (WS3 + WS4) and verify (WS9).
Performance optimizations (pool, ring buffers) come after correctness is proven.

## Risk Assessment

| Risk                                 | Likelihood | Impact | Mitigation                                         |
| ------------------------------------ | ---------- | ------ | -------------------------------------------------- |
| HVF codesign breaks in child process | Medium     | High   | Test early in WS1, may need entitlements on worker |
| shm_open limits on macOS             | Low        | Medium | macOS has generous shm limits, fallback to files   |
| Control socket adds latency          | Low        | Low    | Unix socketpair is <10μs per message               |
| Pre-fork pool wastes HVF resources   | Low        | Medium | Lazy `hv_vm_create()` — only on assignment         |
| Ring buffer complexity               | Medium     | Medium | Start with TAP fallback, optimize later            |
